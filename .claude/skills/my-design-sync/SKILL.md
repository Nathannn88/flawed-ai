# my-design-sync — 设计与素材全量同步

目标：用户只需指出仓库中的新内容或变更路径，后续的分类、冲突检查、传播、索引、记录、依赖修复和旧件退场由本流程完成。

每次执行先完整读取：

- [`config.json`](config.json)：当前目录、权威、依赖、记录与验证配置；
- [`gotchas.md`](gotchas.md)：历史易错点；
- [`references/propagation-matrix.md`](references/propagation-matrix.md)：不同输入的传播提示。

## 不可破坏的边界

1. `design/00-项目核心/最高设计权威.md` 是设计最高权威；输入明确修改最高权威时，才走“权威变更”分支。
2. 仓库 `design/` 是设计文稿和美术源资产的唯一有效源。外部文件是输入或历史证据，不形成并列真相。
3. 法律资料放 `法律文件/`，记录放 `记录/`，不为了“集中”而塞进 `design/`。
4. 代码不得直接依赖 `design/`。运行时素材必须复制或转换到 `config.json` 指定的当前活动实现目录（现为 `prototype/temple-mvp/assets/`）并登记来源映射；未来正式迁移时再切换到 `project/`。
5. 淘汰文件先移入 `design/99-待删除审核/`；用户再次确认前不永久删除。
6. `.base`、`*MAP.md` 与 `design/` 子板块规则已退役；活动导航只认 `design/设计资料索引.md`，设计规则只认 `design/AGENTS.md`／`CLAUDE.md`，不得从历史区或 Git 恢复旧体系。
7. 不静默跳过受影响位置；不自动 push。

## Phase A：摄入与定性

1. 读取用户指定的精确路径；若路径不明确，先从仓库新文件和近期变更定位，不擅自扩大到外部目录。
2. 将输入拆成离散变更单元。每单元标记：
   - 操作：`新增` / `更新` / `替换` / `目录重构` / `素材导入`；
   - 主类别：`项目核心` / `玩法系统` / `世界剧情` / `角色` / `视觉规范` / `美术素材` / `法律记录` / `待整理`；
   - 权威等级：`定案` / `已确认补充` / `提案` / `参考` / `待确认`。
3. 提取实体、别名、旧名、新名和关系端点。图片、模型、PSD 等非文本素材还要记录格式、可见内容、可能用途和是否能可靠预览。
4. 若无法可靠分类，先放 `design/90-待整理/` 并记录缺少什么信息，不凭猜测升格。

## Phase B：影响测绘

1. 阅读最高权威的相关章节和术语约定。
2. 判断分支：
   - 常规变更与最高权威冲突：停止写入冲突设定，向用户说明；
   - 用户明确修改最高权威：新内容成为权威，复核全部下游；
   - 提案或参考：保留其状态，不伪装成定案。
3. 从仓库根全文搜索实体、别名、旧路径、旧名和相关机制词，列出命中位置。
4. 按 `config.json` 的依赖图通读受影响的同级与下游有效文稿；至少覆盖设计索引、素材索引、根规则、PLAN、进度、来源索引、当前活动实现、视觉验收规范和相关 skill 配置。
5. 形成影响清单：`文件:位置`、拟执行动作、为什么需要或不需要改。
6. 只有当变更会改写最高权威、永久删除、改变法律口径或存在多种会导致不同结果的解释时，才停下等用户确认；其余明确且可逆的整理直接执行。

## Phase C：应用变更

- **新增/更新文稿**：写入正确专题文件，统一术语和关联；必要时更新最高权威术语。
- **素材导入**：按建模、场景、角色、道具与供品等当前目录分类，更新 `素材索引.md`；未知源格式或无法预览的文件进入 `待确认/`。
- **替换淘汰**：新内容就位、引用重指、旧件移入待删除审核、清单写明替代物和删除风险。
- **目录重构**：先迁移，再全文修复索引、规则、skill 配置、文档链接、脚本和代码引用；不在易变素材子目录重复创建规则文件。
- **法律/权利材料**：保留在 `法律文件/`，明确 Markdown 编辑源与 TXT/DOCX/PDF 派生关系。
- **代码素材**：只在用户启动实现或明确要求复制时生成运行时副本；副本进入 `config.json` 的 `active_runtime_asset_target`，源与副本关系写入素材索引。正式工程迁移前不得因旧路径惯性把素材写入冻结的 `project/`。

## Phase D：记录同步

1. `记录/进度.md`：更新当前状态、待办、开放问题。
2. `记录/决策与活动日志.md`：
   - 人拍板的结论记 `[决策]`，写清主体、理由和放弃方案；
   - 本次文件变更记 `[活动]`；
   - 只追加新条目，不篡改历史。
3. `记录/源文件索引.md`：更新来源、当前编辑源、派生件与历史版本关系。
4. 长对话出现关键原始需求时提醒用户使用需求快照 skill，不自动调用。

## Phase E：风险自适应验证

先列验收条件、已有证据和未覆盖风险，再按风险做最小充分验证：

1. 检查所有索引路径真实存在。
2. 回扫旧路径、旧名和旧协作口径；历史日志、归档与待删除审核中的旧词允许保留。
3. 检查根、`design/`、`project/` 三对活动 `AGENTS.md`／`CLAUDE.md` 和项目 skill 镜像的业务语义；`记录/v1归档/` 不得进入规则发现清单。
4. 检查是否存在代码直接引用 `design/`。
5. 检查 JSON、Markdown 链接和必要脚本的基本有效性。
6. 若本次设计／素材已经落入 UI、3D、模型、材质、构图、色彩、字体、动效或交互反馈，按 `visual_acceptance_spec` 打开真实页面，主动截图并亲眼分析画风、构图、遮挡、层级、可读性和交互暗示；动态表现优先录屏或至少使用连续截图。仅整理设计文稿时不强行启动浏览器。
7. 浏览器、模型预览或录屏不可用时，将相应验收标为 `BLOCKED` 并写入进度；DOM、坐标、静态图片存在和自动测试不得替代视觉通过。
8. 对跨文件重要改造，如机械证据后仍有语义矛盾风险，最多启动 1 个独立一致性 reviewer；启动前必须走 `my-blind-test` 分流。
9. reviewer 若发现会改变结论的问题，修复后至多做 1 次定向复检；一轮无实质发现后立即停止。

## Phase F：交付报告

交付至少包含：

```markdown
## 设计同步结果

**输入与变更**：……
**权威判断**：定案 / 提案 / 参考 / 待确认

| 文件或素材 | 状态 | 作用 / 处理理由 |
|---|---|---|
| ... | 新增 / 更新 / 迁移 / 待审核 / 查过未改 | ... |

**一致性**：……
**旧引用扫描**：……
**待删除**：仅列入审核 / 已获用户确认后删除
**开放问题**：……
**验证证据**：……
**Git**：未提交 / commit hash；未 push
```

## 学习闭环

独立审查或用户反馈暴露了可泛化漏点时，先查重，再强化 `gotchas.md`。若教训已稳定到应成为硬规则，使用 `official-skill-creator` 修改本 skill，并同步检查 `.agents/skills` 与 `.claude/skills`。

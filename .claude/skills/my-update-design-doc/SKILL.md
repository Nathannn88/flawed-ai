# /my-update-design-doc — 设计文档更新器

> 接收用户提供的设计素材，整理后更新到 `project/设计文档/`。人类可读性优先。

---

## 触发

- 用户说"更新设计文档"、"更新角色设定"、"项目背景更新"、"功能设计"、"UI 方案"
- 用户粘贴了大段设计描述（角色 / 世界观 / 功能 / 交互）
- 用户提供图片并描述为设计参考
- 用户说"帮我整理一下这些设定"

---

## 文档结构

```
project/设计文档/
├── 项目圣经.md     ← 核心文档，所有综合设定的唯一来源
├── 角色资料/       ← 建模文件、立绘参考、形态细节
└── 视觉参考/       ← UI 截图、配色板、动画参考
```

**路由规则**：

| 用户给的内容 | 写到哪里 |
|-------------|---------|
| 综合设定（世界观 + 角色 + 系统混合） | `项目圣经.md` 对应章节 |
| 角色建模、立绘、变形细节 | `角色资料/` 独立文件 |
| UI 截图、配色、视觉灵感 | `视觉参考/` 独立文件 |
| 不确定 | 询问用户 |

> 大多数情况是综合内容，直接更新项目圣经。

---

## 项目圣经章节

固定 8 章，内容随迭代增长：

1. **项目本质** — 是什么、不是什么、核心理念
2. **世界观** — 异世界背景、规则、使命机制
3. **角色** — 每个角色独立小节
4. **产品流程** — 用户体验路径
5. **系统机制** — 成长、付费、事件触发
6. **终局** — 结局选择、分支、不可逆设计
7. **视觉风格** — UI、配色、动画、氛围
8. **技术约束** — 技术栈、API、存储

> 新内容插入对应章节。全新维度 → 追加新章节并告知用户。

---

## 流程

### 一、理解内容

1. 通读用户提供的全部内容
2. 识别涉及哪些章节
3. 简要确认变更范围，等用户确认（用户说"直接保存"可跳过）

### 二、读取与合并

1. 读取当前 `项目圣经.md`（不存在则按章节模板创建）
2. 逐章节合并：
   - 新章节无内容 → 直接写入
   - 已有内容 → 保留原有，补充新信息
   - 有冲突 → 新内容为准，旧内容用删除线标注在末尾
3. 更新顶部"最后更新"日期

### 三、写入与汇报

输出变更章节列表 + 具体变更内容。如有冲突处理，说明新旧对比。

---

## 写作规范

**可读性**：清晰中文短句 · 每概念一行 · 善用列表和表格 · 关键术语首次加粗

**忠实性**：保留用户原始措辞 · 不添加用户没表达的内容 · 不过度概括 · 比喻意象原样保留

**不能做的**：
- 不擅自删除已有内容（冲突时用删除线保留）
- 不修改 `src/` 下的代码
- 不改变章节顺序
